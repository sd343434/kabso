# Kabso Live — Database Schema (Phase 1)

Source of truth: [`apps/api/prisma/schema.prisma`](../apps/api/prisma/schema.prisma) and the
migrations in `apps/api/prisma/migrations/`. PostgreSQL 16.

Conventions: snake_case tables/columns (`@@map`/`@map`), UUIDv7 primary keys generated by Prisma
(`@default(uuid(7))`, time-ordered), all timestamps `timestamptz(3)` (UTC, millisecond precision).
Secrets are never stored in plain form: passwords are Argon2id PHC strings; refresh and
verification secrets are stored as SHA-256 hex.

### `sessions` (owner: auth module) — N:1 users, `ON DELETE CASCADE`

| Column | Type | Notes |
| ------ | ---- | ----- |
| id | uuid PK | also the `sid` JWT claim and the prefix of the refresh token |
| user_id | uuid FK | |
| refresh_token_hash | char(64) | SHA-256 of the current secret |
| previous_refresh_token_hash | char(64) null | immediately previous secret (kept for sessions rotated before v1.2) |
| rotated_refresh_token_hashes | char(64)[] default `{}` | v1.2 SEC-022: last 10 rotated secrets, newest first; presenting any → reuse → revoke. CHECK `sessions_rotated_hashes_bounded` (≤ 10); maintained by the rotation compare-and-swap `UPDATE` |
| rotation_counter | int | incremented on every rotation |

| ip / user_agent | varchar | at creation |

| expires_at | timestamptz | sliding: now + 30 d at each rotation, capped by absolute |

Refresh rotation is a compare-and-swap: `UPDATE … WHERE id = $1 AND refresh_token_hash = $old AND revoked_at IS NULL`.

### `pending_registrations` (owner: auth module — registration) — v1.2 verify-first, KL-019

No account exists until the emailed 8-digit code is verified (contract v1.2 §6).

| Column | Type | Notes |
| ------ | ---- | ----- |
| id | uuid PK | UUIDv7 |
| email | varchar(254) UNIQUE | normalized; **one row per email** (a new register replaces it); CHECK `pending_registrations_email_normalized` |
| username | varchar(30) UNIQUE | reserved while the row is live; CHECK `pending_registrations_username_format` |
| display_name | varchar(100) | already validated (NFC, graphemes, reserved terms) |
| locale | varchar(8) | request locale; CHECK `pending_registrations_locale_valid` |
| password_hash | varchar(255) | Argon2id, computed at register time |
| device_name / platform / app_version, ip, user_agent | varchar | from the register request; platform CHECK |
| code_hash | char(64) | HMAC-SHA-256(key, `email \n code`); key = HKDF-SHA-256(`RATE_LIMIT_KEY_SECRET`, salt `kabso`, info `registration-code/v1`) |
| attempts | int default 0 | per code; consumed atomically before each comparison; CHECK 0–5; reset by resend |
| total_attempts | int default 0 | per pending across resends (v1.2.3 SEC-026); CHECK `pending_registrations_total_attempts_range` 0–10; the row is deleted when `attempts` reaches 5 or `total_attempts` reaches 10 (migration `20261016085446_pending_total_attempts`) |
| expires_at | timestamptz | created/renewed at now + 30 min (`REGISTRATION_TTL_SECONDS`), never past `created_at` + 2 h (`REGISTRATION_MAX_LIFETIME_SECONDS`) |

Index `(expires_at)` for the cleanup job (`REGISTRATION_CLEANUP_INTERVAL_SECONDS`, default 10 min)
plus lazy deletion on register/verify. Not linked to `users` (no account yet).

### `verification_tokens` (owner: auth module) — N:1 users, `ON DELETE CASCADE`

`id`, `user_id`, `purpose` (enum EMAIL_VERIFY \| PASSWORD_RESET), `token_hash char(64) UNIQUE`,
`expires_at` (24 h / 1 h), `consumed_at` (single use; issuing a new token consumes outstanding
ones of the same purpose), `created_at`. Indexes: `(user_id, purpose)`, `(expires_at)`.

### `audit_logs` (append-only)

`id`, `actor_user_id` (FK → users, `ON DELETE SET NULL` so the trail survives deletion), `action`
(`auth.register`, `auth.login.success`, `auth.login.failure`, `auth.login.rate_limited`,
`auth.logout`, `auth.refresh.reuse`, `auth.refresh.invalid_secret`,
`auth.email.verified`, `auth.password.reset_requested`, `auth.password.reset`,
`auth.session.revoke`), `target_type`, `target_id`, `metadata jsonb` (never secrets or raw
identifiers), `ip`, `request_id`, `created_at`. Indexes: `(actor_user_id, created_at DESC)`,
`(action, created_at DESC)`, `(target_type, target_id)`.

## Database roles and rules for new migrations (SEC-011 / KL-013, KL-013b)

The API connects as a DML-only runtime login, member of the NOLOGIN group of its own database,
`kabso_runtime_<database>` (e.g. `kabso_runtime_kabso_prod`); migrations run as the migration role
that owns schema `public`. Details, bootstrap and rotation: `docs/DEPLOYMENT.md` §5.1. The
cluster-wide `kabso_runtime` of KL-013 is legacy: it keeps no members and no privileges in a
migrated database; never grant to it.

Every new migration must follow these rules:

1. **Run it as the migration role** (`MIGRATION_DATABASE_URL`). Migration
   `20261016130000_per_database_runtime_group` set `ALTER DEFAULT PRIVILEGES` for that role, so
   every table and sequence it creates later is automatically `SELECT, INSERT, UPDATE, DELETE`
   (tables) / `USAGE, SELECT` (sequences) for the database's runtime group. **No `GRANT` is
   needed for an ordinary table.**
2. **Never grant DDL-like rights** (`TRUNCATE`, `REFERENCES`, `TRIGGER`, ownership, `CREATE`,
   `TEMPORARY`, `WITH GRANT OPTION`) to the runtime group; the API refuses to boot in production
   if its login holds any of them, directly or through any role it can reach.
3. **The group name is per database**: never write it literally. Derive it in the migration
   and use it only through `format('%I')`, e.g. for an append-only or read-only table:

   ```sql
   DO $$
   BEGIN
     EXECUTE format('REVOKE UPDATE, DELETE ON TABLE public.x FROM %I',
                    'kabso_runtime_' || current_database());
   END
   $$;
   ```

   (as `audit_logs`; the boot guard also checks `audit_logs` specifically). A function the API
   must call needs an explicit `GRANT EXECUTE` the same way: functions are not executable by
   `PUBLIC` (global default privileges of the migration role).
4. **Never reference a login role or a password** in a migration.
5. A migration that grants or revokes privileges, or depends on default privileges, starts with
   the **migration-role guard** below (also in `20261016130000`). It refuses superusers and
   anything that can reach a superuser / `CREATEROLE` / `BYPASSRLS` / `REPLICATION` role, and
   requires the current role to **be** the owner of schema `public` — a mere member of the owner
   would get default privileges registered for the wrong role:

   ```sql
   DO $$
   BEGIN
     IF EXISTS (SELECT 1 FROM pg_roles r
                 WHERE pg_has_role(current_user, r.oid, 'MEMBER')
                   AND (r.rolsuper OR r.rolcreaterole OR r.rolbypassrls OR r.rolreplication)) THEN
       RAISE EXCEPTION 'migrations must run as the migration role, not as "%"', current_user;
     END IF;
     -- (Not in the shadow database of `prisma migrate dev`, which has no _prisma_migrations and
     -- whose schema is owned by pg_database_owner.)
     IF to_regclass('public._prisma_migrations') IS NOT NULL
        AND current_user <> (SELECT pg_get_userbyid(nspowner) FROM pg_namespace WHERE nspname = 'public') THEN
       RAISE EXCEPTION 'migrations must run as the owner of schema public, not as "%"', current_user;
     END IF;
   END
   $$;
   ```

   `prisma.config.ts` already falls back to `DATABASE_URL` only for single-role dev setups; the
   runtime login cannot run DDL, so a missing `MIGRATION_DATABASE_URL` fails closed.
6. Do not change object ownership or create objects in another schema without updating the
   bootstrap and the e2e check `test/security/kl013-db-roles.e2e-spec.ts` ("every application
   table grants DML to the runtime role"), which fails if a table is missing its grants.
